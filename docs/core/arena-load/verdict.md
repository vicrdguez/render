# Verdict

Use Candidate 2 as the base. Do not send either design to builders unchanged.

Candidate 2 makes publication, structural calls, and partial failure explicit. Those choices matter more to Tau's goal than saving one queue. Candidate 1 has better toolchain experiments and several simpler packaging choices. Its promised per-extension atomicity is false. Its options race is real. Its restructure also has definite intermediate gate failures.

## Evidence for each score

### 1. Fidelity

**Candidate 1: 3.** The target layout, one core package, faux identity, runtime imports, and author facade match the brief. See `C1 design.md:79-99,129-184`. It keeps the admin operation off HTTP, retains absent extensions, and preserves saved instructions at `101-127`. It quietly narrows "every project" to open projects. It also changes startup from fail-fast to best effort, without changing the locked prose sentence or identifying the existing startup test that must change. See `C1 design.md:56,99,125,214,247`, `R/docs/core/prose.md:78`, and `R/packages/host/test/projects.test.ts:207-217`. Its source-only plan adds an erasable-syntax restriction. That is explicit, but it is a new authoring limit, not a requirement of jiti. It explicitly removes the accepted websearch testing export at `C1 design.md:188`, but does not amend its accepted-choice record at `R/docs/core/build-notes/attention.md:24`.

**Candidate 2: 4.** Its package and runtime design carries out the main decisions. See `C2 design.md:45-61,90-121`. It keeps all 20 calls and the protocol unchanged at `65,134`. It preserves the options helpers and accepted Webfox limits at `111-115,131`. It names skipped stores rather than claiming to have updated them at `74,88`. It adds conservative task-name, version, and phase refusals at `73`. Those go beyond the minimum reload decision and need explicit acceptance. Its document list is incomplete, particularly for the old direct core imports and the host's statement about not listening to reports.

### 2. Reload is safe

**Candidate 1: 2.** Good preparation, old-code retention, default rebuilding, and pre-due migration warnings are stated at `C1 design.md:105-125`. But `113` promises atomic publication across registries with no failure path. A subscriber can throw after its registry has already changed. See `J/rerun/c2-registry.log:3` and `J/evidence/pi-registry.js:71-75`. The host catalogue is swapped before live installation at `109`, so failure can also leave the options catalogue ahead of a project's registry. No stop or rollback is specified.

The no-lock argument at `117-119` does not cover the captured Options object in an in-flight `setOptions`. `R/packages/host/src/calls.ts:231-244` captures it before awaiting the commit. The old schema can validate and store a value after publication of the new schema. `J/extra-probe.log:9` reproduces that seam. Its live phase check is also stale before publication. Candidate 1 admits this at `C1 design.md:253`. A newly bound project can miss the scan entirely.

**Candidate 2: 4.** The common queue and lock order cover reload, bind, addExtensions, options, setOptions, and workflow create. Publication has no await. An application failure stops the server rather than claiming rollback. See `C2 design.md:67-88`. The definition comparison avoids Candidate 1's phase-inspection race. Both immediate blockage and pre-reservation warnings are included, with later server diagnostics. It is not a 5. Options-schema compatibility and secret metadata loss are not handled. Its report can miss a task that becomes terminally faulted before the second live-task inspection. Startup has no compatibility check against stored checkpoints. Those gaps must not become new safety claims.

### 3. Least machinery

**Candidate 1: 3.** Deriving aliases from the package exports map, disabling the transform cache, a directory-only layout, and source tests are concrete simplifications. See `C1 design.md:85-95,184,261-271`. The W2 experiment supports the source-test choice. But per-extension acceptance creates more composition cases than the text resolves. The live-task veto needs a consistent view that the proposed implementation lacks. Removing the structural queue does not remove its responsibility.

**Candidate 2: 3.** The queue, one catalogue snapshot, and restart-required failure path earn their keep. They concentrate a real ordering responsibility. See `C2 design.md:67-80`. A generation journal and project reopen are correctly rejected at `154`. The new `extension-imports.json` plus generated or checked exports, source lists, tables, and aliases is heavier than necessary at `53`. The package exports map can already own alias keys. Supporting both files and directories adds duplicate rules without a demonstrated caller at `47-49`. Emitting extension tests is defensible for full TypeScript syntax, but it is not necessary for the existing crash-child tests.

### 4. Boundaries by the build

**Candidate 1: 2.** It starts from the existing checker and specifies forbidden workspace imports, raw pi imports, test placement, and pinned public exports at `C1 design.md:154-170`. These are useful. Two concrete holes remain. The new root `index.ts` entry is outside the existing checker's `src` and `test` traversal, `R/tools/check-boundaries.mjs:208-216`. The design never tells the builder to include that entry. Also, its core source closure contains all workspace manifests but not their tsconfigs, while its checker discovers all workspaces. The existing checker reads each package's tsconfig at `R/tools/check-boundaries.mjs:38-40`. The promised stripped core check at `C1 design.md:194` therefore needs a scoped checker, not just a new glob. It has not been designed. Private testing implementation imports and transitive exports also get less protection than in Candidate 2.

**Candidate 2: 4.** It names the actual AST checker, the cases it already covers, symlink and alias handling, testing implementation access, and transitive export checking. It requires negative fixtures first. See `C2 design.md:103-105`. The separated core build and empty installed smoke are explicit at `117-119`. This is a build contract, not merely a statement of intent. It loses a point because the new checker and isolated flake closure were not demonstrated, and the intermediate units postpone changes needed by earlier workspace moves.

### 5. Evidence

**Candidate 1: 4.** The scripts exercise real source, aliases, identity, Webfox resolution, source typechecking, SIGKILL child tests, pre-due migration state, removed phases, and SQLite commit counts. See `C1 probe/README.md:10-24`. I reran the consequential experiments in my own directory. Most results reproduce. The missing qualification is important: zero commits with two not-yet-due sleepers does not prove that stores stay unchanged through a live reload. The synchronous install is storage-free. Scheduler work triggered by it is not. See `J/extra-probe.log:5`. The cache location also depends on the importer location, not just TMPDIR.

**Candidate 2: 4.** Its collision, subscriber-failure, and migration experiments reproduce. See `C2 probe/registry.mjs:16-51`, `C2 probe/registry.log:2-9`, and `J/rerun/c2-registry.log:2-9`. It properly calls the 283-test run a baseline rather than evidence of the new design, `C2 probe/README.md:18-24`. It covers unmeasured concurrency by serializing it, not by asserting pi handles it. It does not measure a removed phase, but its same-version definition veto avoids relying on that behavior. It misses jiti's file cache and has no target-layout or facade compilation probe. Those omissions prevent a 5.

### 6. The restructure is buildable

**Candidate 1: 2.** Its 14 named units and explicit test disposition are useful at `C1 design.md:228-247`. They do not leave the gate green as promised. Unit 6 deletes kit before units 7 and 8 convert its callers. Unit 9 links package directories containing emitted JavaScript through a loader that rejects such files. Unit 10 moves the core before the flake is retargeted in unit 13. Unit 14 has no explicit failing check. Details are below.

**Candidate 2: 3.** Each unit names contract tests and the fate of the 283 tests is better enumerated. See `C2 design.md:136-148`. Unit 3 couples directory moves with references, assets, lock, and flake changes, which is necessary. But units 1 to 3 are too broad for one minimally informed builder. Unit 2 introduces a journey workspace before unit 3 changes workspace discovery. Unit 5 introduces usable publication before unit 6 installs its partial-failure shutdown. Its intermediate gate and safety boundaries need repair, not just a final cumulative run.

### Other locked-design changes and document gaps

1. **Startup failures.** Candidate 1's best-effort start is a behavioral change from both the current static imports and `prose.md:78`. Its planned new `host.md` paragraph records skipping, but its exact sentence table never updates prose.md. Its test migration list also misses the existing name-mismatch refusal test. Candidate 2 preserves fail-fast start and updates the prose sentence at `C2 design.md:132`.
2. **Task names are currently unique per registry, not per whole server.** Both candidates dry-install the whole server catalogue in one scratch registry. They therefore reject two extensions with the same task kind even if no project selects both. This is an unacknowledged tightening relative to `R/docs/core/primitives.md:288,310` and the per-project registries in `R/packages/host/src/projects.ts:229-266`. Keep it only as an explicit authoring rule or validate actual project selections.
3. **Task evolution.** Candidate 2 explicitly forbids deleting a task kind or lowering a version at reload. Candidate 1 only vetoes a currently observed missing phase at the same version. These are new reload refusal rules, not substrate guarantees. Candidate 2's conservative rule has a concrete benefit: old work cannot enter a phase dropped at the same version while preparation yields. It also refuses harmless deletion when no stored work or decision needs the kind. The owner should accept that burden knowingly.
4. **Report logging.** `R/docs/core/host.md:220` says the fault feature does not listen to onReport. Candidate 2 adds a callback at `86`, while keeping fault scans authoritative. This is a reasonable distinction, but the locked sentence needs a narrow amendment. Candidate 1 leaves later reporting an open question at `277`.
5. **Author import wording.** Candidate 2 does not replace `R/docs/core/primitives.md:264`, which still says extensions import directly from core. Its root package remains importable, so this stale nearest example matters. Candidate 1 names this edit at `219`. Candidate 2 also leaves the host's "does not import the kit" wording implicit. Both should update the kit naming paragraph, not only its opening paragraph.
6. **Websearch testing.** Candidate 1 explicitly deletes `tau-websearch/testing` and generates an absolute-source fixture. That is a real reversal of the accepted choice in `attention.md:24`. It should be recorded there. Candidate 2 retains the export with a journey-only policy. Neither should broaden production cross-extension imports to make the fixture compile.
7. **Sources and options.** Candidate 1 narrows supported TypeScript for its source test runner. Candidate 2 does not. Both preserve the existing rule that incompatible stored options can fault work, `R/docs/core/kit.md:158`. Neither repeats that rule in the reload procedure, and neither handles removal of secret metadata. No automatic option migration is authorized by this brief.
8. **No protocol loophole is used.** The admission rule is `R/docs/core/README.md:84-94`. The version rule is `R/docs/core/protocol.md:198-202`. A new HTTP call would not necessarily require `/v2`, but it would still need admission. Neither candidate adds one. Both correctly use the owner-only admin socket instead.

The global name restriction, skipped-store scope, runtime validation limits, and secrecy consequences are not resolved by saying that everything else remains unchanged.

### Two publication details builders must not infer

- An install throw does not always mean no install. Validation throws before publication. A subscriber throw is after publication. Candidate 2 measured the distinction. Candidate 1 did not.
- Candidate 1's scratch ordering can differ from live Project ordering. Suppose A drops task x and B gains x. A then B can validate the final scratch state. A project ordered B then A can fail while B is installed against old A. Candidate 1 allows task deletion and gives no intermediate-state rule. Candidate 2's task-deletion veto prevents this transfer case, at the cost already noted.

## What both left out

1. **A complete options-upgrade contract.** Preserve the documented invalid-value behavior. State what reload prints about it. Add a check that changing schema metadata cannot reveal a previously secret stored value. The real failure is measured, not a theoretical attack.
2. **The tool collision rule.** Last selected provider wins. State it and test the intended Project-order default. A new global ban would be a new policy, not a free registry check.
3. **A precise nested-validation boundary.** Decide which malformed module cases loader preparation rejects and which remain trusted author errors. Give builders concrete negative fixtures. Do not grow a second pi Extension implementation.
4. **Recovery limits in owner language.** Restoring files and restarting can restore code availability. It cannot undo task effects or revive terminal task IDs. A missing phase is not a repairable migration block.
5. **A coherent skipped-store outcome.** Either refuse incomplete application or explicitly report partial coverage of open projects. Never print that every project was updated when a store was skipped. Do not add a forbidden reopen operation to hide this gap.
6. **All relevant entry files in the import gate.** Include root wrappers, test implementation files, generated deployment fixtures where applicable, and inherited compiler configuration. A rule that only scans the old src/test layout is not sufficient after changing entry layout.
7. **A complete document/test migration inventory.** Fix all contradictory current sentences in the same unit as the relevant contract. Preserve historical arena documents. Record the fate of each existing test, not only each package.
8. **A proven installed source-deployment closure.** Both describe it. Neither built it. Verify external source loading with no local node_modules, correct facade identity, Webfox, prose, a core-only check, and installed reload through admin.sock before handoff.

## Questions only the owner can answer

1. Should one invalid extension prevent startup of the whole server, or should startup continue with that extension missing? Candidate 2 preserves the current fail-fast behavior. Candidate 1 prioritizes availability. This is a policy choice, not a measurement question.
2. May extension authors be restricted to erasable TypeScript so tests run directly from source, or must enums and other jiti-supported TypeScript remain supported? The noEmit option is measured. Its syntax restriction still needs acceptance.
3. Should reload reject task-kind deletion and version downgrade even when no live task needs the old definition? Should task kinds be globally unique across the server catalogue or only within projects? Candidate 2's conservative rule reduces risky publication cases, but it is an added compatibility burden.
4. Is restart an explicit unsafe override for checkpoint compatibility, or should known incompatible stored checkpoints remain parked at startup? Neither design currently protects that restart path. Permanent faults cannot be repaired just by restoring code.
5. If startup skipped a store, should reload refuse incomplete coverage or apply to open projects with a skipped-store warning? No answer should imply a per-project reopen command.

These questions do not reopen the 20 calls, the faux identity requirement, the one-package author surface, or the accepted sample defects.
