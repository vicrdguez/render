# Rubric (the picker's tool; candidates never see it)

Score each criterion 1 to 5 with quoted evidence.

1. **A list an engineer can build from.** Every capability names what it takes, what it gives, what it is built on, and what a resend does. W0 is covered. Nothing in it designs a client, a wire format, or a transport (ruling 12).
2. **Legal on pi-durable.** The calls exist as cited, and each commit keeps the legal order. Check at least three load-bearing claims against source. A probe that ran counts for more than a citation.
3. **Options meet the owner's ask and the failure cases.** One function defines and reads. Values are per project with no work for the workflow author. The storage choice is argued with evidence against the alternatives, the owner's JSON file included. A client can change a value, and the host checks it. A crash, a rerun, running work, and the first conversation's model are each answered.
4. **Small, and by the rules.** Each core change gets an honest pass or fail on the five checks. The library part gets the four checks. The host still knows no workflow, and the store layer still knows no project. Nothing is designed that the rulings did not ask for: no clean-up, no retry, no client.
5. **The script holds.** Each of the nine steps is walked with its commits. The odd points are handled or honestly marked: the retried create, the option changed during a review, the failed run, the faulted task, a workflow added to a project with live work, and the restart.
6. **Candor and evidence.** Labels are used correctly. "Not verified" is complete. Nothing is claimed as run that was only read.

Then answer:

- Which candidate is the best base for the next version of `docs/core`?
- Which one or two ideas from each other candidate are worth porting?
- Where do candidates disagree on a fact, and who is right?
- What did every candidate miss?
