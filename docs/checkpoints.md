# Exact editable technical checkpoints

Seams and Modules are technical decisions, not Contract acceptance. The human alone approves them in this version. Persistent routing settings, final intake acceptance, candidate comparisons and protocol experiments belong to later capabilities. A request declaring required candidates or experiments refuses synthesis with a named capability blocker; generic role reports do not waive those requirements.

## Owned interfaces and sequence

All commands use the existing version-1 Ledger envelope, workflow, authority epoch and durable command ID. The `checkpoint` Engine tool accepts a JSON command string; Ledger establishes the actual assignment principal. Tool arguments cannot impersonate a human or host.

1. Schedule a read-only design coordinator with explicit human Ground in `packet.inputs`, full principles/instructions and a configured read-only challenger in `packet.requests`. Investigation assignments cannot silently become design coordinators. Human-authored Ground bytes establish the cited scope; assistant proposals do not.
2. `requestCheckpoint {stage, scope, required:{candidates,experiment}}` creates one pending request for `seams` or `modules`. A different command ID, coordinator, or principal cannot create a second pending same-stage identity. Requests capture human routing and an applicable policy binding. Modules additionally capture the current approved Seams.
3. `stageCheckpoint {request,text,manifest}` retains the complete immutable Markdown and regenerated typed manifest under separate artifact refs. Manifest schema 1 includes nodes (`id`, `decision`, `rationale`, distinct `alternatives`, exact retained `evidence`, `classification`, `default`), decomposition comparisons (`id`, `modules`, `dependencies`, `verificationSeams`, `depth`, `locality`, `deletion`), `verificationStrategy`, `incidentalChoices`, and concern `responses`. Seams requires two distinct comparison identities. Typed lint cannot prove genuine conceptual difference or prose merit: the challenger and human judge those.
4. `requestCheckpointReview {request,key}` uses the configured challenger template in a fresh workflow-owned assignment/conversation, with exact emission, manifest and concerns in its inputs. The coordinator durably waits for the child. Required-family availability remains Engine-checked; different-family policy is the default. Same-family review needs an explicit retained human policy direction and is still a distinct non-fork context. Cancellation/replacement of a failed reviewer preserves the original review basis and complete retained input set.
5. The challenger submits its own report via `submit_role_result`. Required JSON fields are `schema:1`, `emission`, `manifest`, `annotations`, `checks` (reasoned alternatives/interactions/scale/usage/incidentalChoices/nearbyCopying), and stable `objections:[{id,node,reason}]`. The packet supplies these questions; model claims are not trusted execution facts.
6. `emitCheckpoint {request,review,contested}` answers every objection (`objection`, `disposition`, `reason`, resulting node ID). Exact report payload **and trusted assignment basis** must match. New bytes require another staging and fresh review. The emission becomes eligible for human decision, never automatically accepted.
7. Human `approveCheckpoint` supplies `request`, `emission`, `manifest`, numeric `annotations`, `policyBinding`, explicit node-to-alternative `decisions` and `nonbinding` concern IDs. The common validator binds this exact basis. Saving unrelated evidence does not stale it; applicable policy adoption does. Read the current checkpoint in the workflow snapshot after a stale-basis refusal.

## Complete saves, dispositions and races

`saveCheckpointConcern {request,base,text,kind?}` is a human command. `text` is the complete UTF-8 Markdown string (including empty edits, BOM/CRLF when present), not a patch; `base` identifies a retained emission of that request. `kind:"reason"` saves a nonempty separate human reason. Editable identity-like frontmatter is content, not authority. Each submission is independently retained with its own stable concern ID, edited artifact and lossless whole-document replacement hunk/diff. A whole-document hunk deliberately avoids claiming semantic annotation extraction. A coordinator may address multiple issues in one submission but must disposition that complete submitted concern.

Every acknowledged submission survives. Multiple submissions on the same base expose a conflict instead of overwriting. Saves against earlier retained emissions remain legal after re-emission. The next manifest maps every stage concern to `acted-on`, `considered` or `dismissed`, with reason and resulting node. `reworkCheckpoint {request}` requires a previously saved edit or reason and keeps the same request/routing basis.

Save never means consent. Save-first increments the annotation revision and refuses old-basis approval. Approval-first retains the approved original and marks the later save as a change request. Approve-with-notes supplies **all** saved concern IDs as explicitly nonbinding and accepts only original emitted bytes; it does not accept an edited artifact. Reworking notes into binding content requires a newly staged manifest and exact review.

`cancelCheckpoint {request,expectedEmission,reason}` is an explicit human cancellation. Stale emission cancellation refuses. Cancellation preserves all bytes/concerns and permits a successor request, without silently rerouting pending work.

## Revised Seams and continuation

Requesting revised Seams blocks affected delivery/writer and implementation/review assignments whose explicit inputs cite the prior approved Seams/Modules artifacts or manifests. Read-only design coordinators, challengers and candidate/experiment roles may still read historical evidence needed to obtain the revised decision; reading evidence is not delivery authority. Executing assignments become blocked without pretending their processes are quiescent; existing Engine stop/quiescence handling governs capacity and workspace reuse. Unrelated inputs do not block. Current Modules approval also refuses until the revised Seams decision. Historical approvals and their exact decision records are never overwritten. After a revised approval, old-basis execution remains invalid; cancel/quiesce and explicitly replace affected work with the newly approved input basis. No Contract amendment or acceptance is fabricated.

Close/reopen the same data directory using ordinary host startup. A fresh client snapshot exposes requests, emitted refs, concerns, owners, blockers and next human action; no old chat is needed. Scoped history/export includes all checkpoint revisions, diffs, manifests, decision commands, role reports and provenance as immutable documents/facts. Unsaved editor buffers are not durable. Missing/corrupt exact supporting content refuses the affected command and names its ref; never refetch or substitute newer bytes under an old identity. There is no disaster-recovery package/import/repair path.

## Verification and limits

`npm run verify:editable-checkpoints` runs pure Kernel and real-SQLite/Engine scenarios. The preimplementation failure matrix is `docs/verification/editable-checkpoints-failure-cases.md`. The repository catalog distinguishes existing process/HTTP coverage, scoped role durability and this checkpoint composition through two authenticated HTTP device clients, including concurrent edit/approval and 10,000 seeded exact-basis schedules. Unsafe controls individually reject edited-byte approval, lost acknowledged concerns and stale exact challenge. Scripted providers establish scheduling/provenance and structural checking, not model judgment quality or an observed human handover. Final Contract acceptance, candidate/negative-experiment journeys and full source-delivery V9 load are not delivered by this checkpoint capability.
