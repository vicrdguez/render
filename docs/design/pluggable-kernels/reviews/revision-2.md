## Clarifications from the reviewers' risk lists

- A missing selected procedure case in the pinned content release is a blocker, never a fallback.
- Workflow maintainers make compatibility claims through normal human-reviewed releases. Host installation and project content adoption do not certify semantic equivalence. No per-agent approval stage was added.
- Adding a procedure with existing mechanics can require a workflow selector change without an Engine change. A changed behavior is not compatible merely because it edits prose or passes a schema check.
- `prepareTask` is pure and receives facts about facilities, not I/O handles. Host-supplied capabilities cannot be replaced by workflow output.
- Pins apply to a prepared-assignment revision. Same-assignment continuation can gain a linked revision for a new authorized basis without changing pinned authored sources.
- Authorized model changes, compaction, and reset preserve refresh or explicit staged-read requirements. Unsupported model changes remain blocked.
- The workflow owns the guidance-selection policy and identifies the responsible preparation role. Project administrators supply adopted guidance. Unresolved required relevance cannot produce a ready plan.
- Project creation retries use host scope and original request identity before resolving changed defaults.
- Historical knowledge inspection is distinct from new assignment adoption. Derivative-record reuse after revocation is an explicit remaining product decision, not an inferred permission or a promised content-tracking system.

The storage adversary reported no confirmed contradiction or false current-source claim within its scope. It did not prove a working project isolation system. The instruction adversary reached its turn limit after writing its report; the review is bounded, not exhaustive.
