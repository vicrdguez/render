## New annotations

### R3-A001 — One Audit per implementation pass, including Watchdog rework

- **Type/status:** explicit human clarification and selected correction to r3's broader once-across-the-Slice interpretation. Supersedes affected lifetime/count wording in R2-A006/R2-A010 and its r3 application; preserves Audit inside implementation before final sealing/submission.
- **Human wording, verbatim:** "Audit’s purpose: fresh-context assistance before each implementation handoff, without letting Audit’s own findings generate an endless inner review loop. So in essence, yes we want one Audit per implementation pass, before every handoff to watchdog".
- **Selected boundary:** each implementation pass gets one logical Audit with fresh Standards and Contracts contexts. The implementer addresses its findings and reruns relevant checks before sealing/submitting that pass. Audit findings do not schedule another Audit within the same pass.
- **Watchdog rework:** a Watchdog return to implementation starts another implementation pass, which has its own fresh-context Audit before its next handoff. Do not retain the first completed Audit as a substitute for Audit on all later passes merely because the Slice, Assignment or implementing conversation continues.
- **Example:** implement pass 1 → Audit 1 on A1 → fixes/rechecks → B1 → preparation/checks X1 → Watchdog requests rework → implement pass 2 → Audit 2 on A2 → fixes/rechecks → B2 → preparation/checks X2 → Watchdog. There is no Audit-1/fix/Audit-1-again inner loop. Preserve both reports and their actual source provenance.
- **Preserved semantics:** same-pass interruption/recovery resumes the existing incomplete invocation, rather than inventing a new pass just to rerun Audit. Audit still does not count toward Watchdog's completed-review cap. Each Audit report identifies the pre-fix source it actually inspected; later fixes and preparation are not relabeled as audited. No post-preparation exact-X Audit gate is reinstated.
- **Pass definition:** bind Audit lifetime to actual implementation passes, not a global Slice-only prohibition or process/container restarts. Make transitions into a new implementation pass explicit, including how preparation-conflict repair relates to that boundary. Pure deterministic preparation/target-drift retries without a new implementation pass are not separately resolved by this clarification; do not silently interpret the handoff wording as requiring a post-preparation Audit or preserving the rejected once-per-Slice rule.
- **Required revision:** correct §1's delivery-order description where needed, §3 I8/I19, §6.2/§6.2.1 roles/lifetime, §8 delivery/verification text, §11 Audit/conflict/drift/rework traces, §13 checks/negative controls, §14 plan and the current disposition. Replace the explicit prohibition on new Audit after Watchdog rework. Fresh-context assistance before each implementation handoff is the purpose; avoiding Audit's own endless inner loop is the count limit.
- **Session handling:** the preceding question alone was explicitly not to be annotated; this annotation records the subsequent affirmative human direction. Source spec/dispositions remain unchanged during the walkthrough.

### R3-A003 — Select the recommended three-layer web-evidence retention policy

- **Type/status:** human selects the selective-evidence recommendation after its walkthrough, resolving the remaining web-retention direction in R2-A004. Not overall spec acceptance or a new general history-pruning policy.
- **Human wording, verbatim:** "I like the recommendation", in response to the selective-evidence versus complete-result retention explanation.
- **Selected policy:** (1) bounded, assignment-scoped working caches/large-result files may expire or disappear after restart; (2) ordinary committed bounded Durable tool output/provenance remains under the native runtime history contract; (3) exact relevant passages and enough context are explicitly retained in Ledger before a report/checkpoint/decision relies on them. No default permanent archive of every complete search/page result.
- **Evidence quality/provenance:** retain the material needed to inspect the claim, including relevant negative/conflicting evidence, with source URL, observation time, query/request and provider/extractor provenance, digest and completeness/truncation labels as described in §6.6. Retain the whole page when actually needed to inspect/reproduce the claim. A URL/digest alone cannot recover missing text. Use existing Ledger artifact handling, not a second web database or a formal human approval for each evidence selection.
- **Expiry/refetch behavior:** an expired/unavailable handle reports that state. Refetch creates a new observation with a new identity/time; it must not replace old bytes silently under an old reference. Cache cleanup cannot erase committed output, retained evidence or acknowledged document history. A missing required supporting passage is an evidence gap, not a substantiated claim.
- **Accepted trade-off:** a later investigation may need nonpromoted surrounding/full material that has expired, changed or disappeared, requiring a new request and possibly additional cost. Complete-result archiving would improve later reuse but is not the selected default. Do not disable normal web-tool result commits/replay history as an alleged simplification.
- **Unselected implementation details:** no numeric cache lifetime, quota, physical cache backend, privacy-deletion schedule or change to accepted D006/R2-A009 document-history retention follows. Keep those details proportionate; do not introduce an unrequested archival subsystem or extra approval flow.
- **Required revision:** mark selective web evidence retention as selected in §1/§6.6, §11 web restart history, §12 recommendation status, §13 checks, §14 and the current disposition. Combine with R3-A002's selected Webfox/Exa/Tavily setup; backend/provider and retention are no longer unresolved product choices. Preserve bounded experiment limitations and actual production integration checks.
