# Keel cross-judgment

**Use B's lane interfaces and Git protocol as the base, not its entire first slice.** B distinguishes three things that can change independently: the edition the owner approved, the assignment under which a worker acted, and the commit the verifier actually checked. A has the better way to make withdrawing an obsolete question automatic. Neither sketch is build-ready as written.

## 4. Fact check

`PD` below means the installed `node_modules/@earendil-works/pi-durable/dist`. These are source checks, not crash-test results.

- **A, task dispatch:** `dispatch/index.ts: DispatchOwner.commit<T>` returns the callback's arbitrary value. A tool can do that; `PD/types.d.ts: TaskRuntime.commit` accepts next task state or `undefined` and returns `Promise<void>`. It needs an adapter that also commits phase progress. `RoleSettings` doesn't require closed tools/modelTools (`core/src/extension/helpers.ts: role`); `PD/harness/agent.js: createAgent` copies the parent's agent. Explicitly replace inherited selections. Refusing *all* task-owned callers also excludes legitimate reusable parents, not just dispatch children.
- **A, owner input and stop:** `core/src/host/calls.ts: input/stop` never invalidate a Keel decision; `PD/harness/submissions.js: admitSubmission` can queue an input before it has a transcript entry. An owner can message a worker, then answer the still-open decision **before a lane tool fires**. Matching the decision ID prevents a duplicate continuation, not this stale first application. Conversely a chat message is not informed authorization for `settled_by_owner`. A repeated `conversation.abort()` can stop newer work (`docs/host.md: Conversations`). The example host `answer` also omits required `basis` (and `project`).
- **A, storage:** `kernel/state.ts` sketches `changesSinceBase`; `PD/types.d.ts: CheckpointInfo` calls it `deltasSinceBase`. The actual doc token carries `definition` and session/task docs don't take conversation `history/fork`. Two stated uncertainties can be narrowed: task doc creation checks existence/nonterminal status, not task kind, and terminal settlement retires those docs (`PD/session/transaction.js`, around 402 and 692). `api.commit` delegates to `runtime.commit`, whose run gate rejects a durable abort mark (`PD/harness/tool.js:337`, `scheduler.js:2721–2740`). This is not a rollback of effects already performed.
- **A, capability claims:** `roles/index.ts` gives Bash even to readers. Per grounding §10 it can modify files, refs, protected prose and the host environment beyond cwd; checking a diff at publish cannot prevent that. Configurable `base != trunk` also does not, by itself, prohibit `trunk=main` if base is renamed. Neither provider name nor a role option proves independent authorship.
- **B:** Its two narrow corrections to grounding are correct: `admitSubmission` rejects a reused ID of another **type**, not different text of the same type, and an immediate display-only write can queue behind a reset. `LiveDoc` is exported by `core/src/extension/durable.ts`; its `run.inputs` and `runFailure` are real, **not** an input-admission veto (`PD/harness/live.d.ts`). B explicitly does not promise stock Tau rejects every raced answer. `docs/host.md: Calls` supplies no arbitrary Mark gesture, sandbox or model-family catalog: B's inlet convention, runner and family mapping are prerequisites, not platform facts. No core change is justified by either design.
- **B, Git (not a Tau guarantee):** A successful multi-ref `update-ref` is useful, but don't infer that two loose refs are one crash-atomic record. Git's [update-ref manual](https://git-scm.com/docs/git-update-ref) allows a reader to see a subset; the [files backend, `files_transaction_finish`](https://github.com/git/git/blob/v2.50.0/refs/files-backend.c) finishes refs in a loop. Killing only the server need not kill the Git child. Inspect the target **and** witness after the writer settles; a mixed/ambiguous observation is not proof of landing. With one reserved writer, persisted old/new plus a single trunk CAS may be enough.

## 6. Base, grafts and cuts

Use **B**. Adding a second worker shouldn't invalidate the first worker's proof, and adding a new verdict tool shouldn't give its caller the right to name a trunk hash. B offers the right units to enforce both. Its stable block IDs and per-fix observations also distinguish “this fix failed twice” from “this reviewer has appeared three times.” Both candidates converge on root-conversation work identity, project-local queue, code-owned lane crossings, a separate first submission, and foreground task-owned dispatch. Keep those, not a new Tau subsystem.

Port two ideas from A:

1. **Derive outstanding owner questions from the stored situation** (`Lane.asks`). In B, compare the old/new slot for the subject being changed and withdraw/supersede in the same turn. Keep B's check on the *actual answer*, since raw client input need not change a lane. Don't port `World` or an all-lane reconciler.
2. **Declare the model's tool arguments beside their trusted conversion to a lane message** (`ToolSpec`, `build/tools.ts`). Preserve B's tickets, restricted file tools and actual Git/check receipts. Have one typed registration generate the role menu and require receipt/admission for every publication; don't port `unknown` schemas, erased registries or the owner-message bypass.

Before implementation, give B's Git completion the decoded purpose and give read-before-write handlers the specific immutable facts they need. Assign the review map and operation checkpoints real addresses. Cut the universal file mutation journal and all-purpose `Turn` privileges from the lane interface. The workflow isn't under-specified about never writing main, protecting proof or investigating findings. It **is** under-specified about what a raw message invalidates, what execution environment can attest proof, and who else can move/own trunk. Those are the three owner rulings with the largest downstream cost.

## 7. Simplest viable version

One project/repo, one active item per build, a small pending list, one coordinator, one worker, one independent verifier. Run a precedent-following repair through one actual red test, one ruling, a blocked verdict, in-place fix, full check and single-commit handover. Store the prompt/edition, assignment, reports, per-finding fixes and current question; use a tool-task receipt, a decision-ID guard and a post-commit drain. No raw shell with live credentials or writable protected checks. Use an **existing owner-approved isolated runner and narrowly fenced edits**; if no such runner exists, run only in a disposable credential-free test project and do not call that production proof.

Keep the two narrow Git invariants from day one: commit intended work **before** touching Git, and install exactly the checked commit by expected-old CAS with recoverable ownership evidence. Refuse an unknown checkout rather than repair it. A simple single-holder slot suffices before FIFO scheduling is needed. Test both kill points against real SQLite/Git, replay of a publication and replacement answer, stale direct input, cancellation, and a second surviving fix leading to fresh diagnosis/one investigated queue row. Do not defer these failures: the task already names them.

Defer multi-item planning UI, queue batching/standing Mark inlet, all-day watchers/nudges, universal page/upcaster machinery, per-edit private-index snapshots, full arena/prototype tooling, scheduled sweeps and witness GC. Use explicit typed records at version 1 and add migrations when a shape changes. For slice-one questions, check authority at answer time and use a fresh basis after redirection; if the owner requires immediate disappearance from a generic Tau inbox, the active withdrawal mechanism is **not** optional. Run the independent 51-trigger and Minos Ground replays before trusting routing. This is a delivery slice, not a claim that later workflow requirements can be dropped.
